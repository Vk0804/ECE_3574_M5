#M5 Decision Record - 500 words 


There are three threads in the application. The GUI thread owns the widgets, the Workspace, and all of the state objects. The build worker is a std::thread that BuildManager starts in its constructor and joins in shutdown(). It runs BuildManager::worker_loop() to handle build requests in the background. The CR-1 server runs on a separate thread and only posts add_document_file() to the GUI thread using a queued call. This means the server does not directly access the GUI or share data with the build worker.

The GUI thread and build worker share three members of BuildManager: pending_request_, generation_, and stopping_. All three are protected by the same mutex, mutex_, and the worker uses condition_ to wait for new requests. Each member has a different purpose. pending_request_ stores what needs to be built, generation_ tracks whether the current build is still wanted, and stopping_ tells the worker when it needs to exit. These three members are necessary because they each handle a different part of communication between the threads. The Workspace is copied into the build request, and the finished ProcessingCore is sent back through a queued call using a shared_ptr, so neither is directly shared between the threads. The building_, result_, and result_version_ members are only accessed by the GUI thread.

The application uses three states: ReadyState, BuildingState, and ExitingState. When the application is in ReadyState, no build is running, so the user can start a build or make changes to the workspace. Starting a build moves the application into BuildingState. While a build is running, another build request is rejected and the Build Corpus button is disabled. If the workspace changes or the user clicks Reset, the current build is cancelled and the application returns to ReadyState. When a build finishes, its result is either accepted or discarded before returning to ReadyState. Finally, ExitingState handles application shutdown and ignores any additional requests. Each state is implemented as a separate class in main_window.cpp, and MainWindow::transition_to() switches between them by replacing state_.

When Reset is clicked during a build, the GUI calls reset_application(), which sends the request to BuildingState::reset_requested(). This calls BuildManager::cancel_build(), which locks the mutex, increments generation_, clears pending_request_, and notifies the worker through condition_. The worker wakes up from its wait_for() because the generation no longer matches the original request. It then stops processing the current document loop. Since request_cancelled() returns true, the worker does not post a completion result and goes back to waiting for another request. At the same time, the GUI resets the workspace and transitions back to ReadyState. If an old build completion reaches the GUI later, handle_completion() checks its generation and discards the outdated result.

One design decision was to reject build requests while another build is running. This prevents multiple builds from running at the same time and avoids conflicting results. Another decision was to cancel the current build if a document is added remotely. The remote request reaches add_document_file(), which calls BuildingState::workspace_changed(). This cancels the build, returns to ReadyState, and displays "Workspace changed. Build the corpus again."

I also added two fault switches to test the threading behavior. AIWS_FAULT_NO_CANCEL was intended to disable the normal cancellation behavior in request_cancelled() and the wait_for() predicate in worker_loop(). However, during testing, the fault-injected version still appeared to reset the application in the same way as the normal version, so I was not able to confirm that the fault was working as intended.
